### Bulk panel "Load more" — silent truncation on long histories

- [ ] [FIX] `scrollUntilStable` gives up long before the sidebar is fully loaded, returning a silent partial list (violates AGENTS.md #4 — fail loud on extraction). Verified live 2026-07-24 on a 1042-conversation account: replaying the shipped algorithm with the shipped constants (`SCROLL_STEP_DELAY_MS = 150`, `SCROLL_STABLE_ROUNDS = 3` — `src/adapters/chatgpt/index.ts:17-18`) returned **19 of 852** top-level `/c/` conversations after 4 steps and **returned normally** — no `ExtractionError`, so the bulk panel would silently offer 2% of the history as if it were the whole list. Root cause: `#history` lazy-loads the next page from the server, and the measured round-trip is **1418–2830 ms** (4 consecutive batches, 2026-07-24), while the stall window is only `stableRounds × stepDelayMs ≈ 450 ms`. Three no-progress rounds elapse well before the batch lands, so the loader reads "no new items → fully loaded". A patient replay (1500 ms/step, 8 stable rounds) reached 852 top-level (1042 counting project/GPT-scoped rows) and settled at the true bottom, confirming the list itself loads fine. Affects `loadMoreConversations` and `loadMoreProjectConversations` (both call `scrollUntilStable`, `src/adapters/chatgpt/index.ts:778`). Fix must make the stall window exceed real lazy-load latency with margin, and should distinguish "no new items" from "still fetching" rather than relying on wall-clock patience alone. `collectVirtualizedTurns` is NOT affected — it terminates on actually reaching the container bottom, not on count-stability.
- [ ] [TEST] Regression coverage for the above: the existing suite (`test/adapters/chatgpt/load-more.test.ts`) resolves lazy batches synchronously, so a stall window shorter than the fetch latency passes. Add a model whose next batch arrives only after a delay exceeding the stall window, asserting the loader keeps waiting instead of returning a partial.
